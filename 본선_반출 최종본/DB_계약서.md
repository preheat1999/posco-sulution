# AI 자재 솔루션 · DB 계약서

기준일 `2026-09-03` · 자재 743종 · 부서 1 · 설비 14 · 정비계획 156행

> **먼저 읽을 것** · 당일 진행은 `00_시작하기.md`,
> 붙여 넣을 프롬프트는 `프롬프트/` 폴더에 있다.
> 이 문서는 **규격**이고, CLI 에게 「이걸 먼저 읽어」 라고 줄 참고자료다.

이 문서는 **화면과 데이터 사이의 약속**이다. 화면을 새로 만들더라도 이 약속만
지키면 화면끼리 어긋나지 않는다. 어긋나면 안 되는 것을 「불변식」 으로 적어
두었고, 검사기가 그 다섯 개를 자동으로 본다.

---

## 0. 왜 이 구조인가

한 번 크게 틀렸다. 화면마다 자기 더미 자재를 들고 있었다. 그래서

* 적정재고 화면의 자재와 반납 화면의 자재가 **교집합 0종** 이었다.
  「분석에서 본 자재를 반납해 보자」 라는 흐름이 아예 불가능했다.
* 같은 코드가 화면마다 다른 자재였다. 한쪽은 Wear Plate, 한쪽은 Slew Bearing.
* 생성기가 셋이라 한 파일만 옛 판정으로 남았다. 자재 검색은 보험품 441종,
  다른 화면은 302종을 보고 있었다.

그래서 **자재 하나의 정체는 한 곳에만 둔다.** 그게 이 계약서의 전부다.

## 1. 3층 구조

| 층 | 무엇 | 쓰기 | 수명 |
|---|---|---|---|
| **1층 정본** | 사내 원장 스냅샷 · 자재 · 부서 · 설비 · 정비계획 | 생성기만 | 대회 내내 고정 |
| **2층 파생** | 알고리즘 초기 판정값 · 속성 · 등급 · 목표재고 · 신호 | 생성기만 | 대회 내내 고정 |
| **3층 오버라이드** | 사람이 화면에서 한 일 · 승인 · 반납 · 공용전환 | 화면 | 브라우저에 누적 |

**원본을 절대 덮지 않는다.** 승인도 반납도 3층에 이력으로만 쌓는다.
화면이 보는 현재 값은 매번 `1층 + 2층 + 3층` 을 겹쳐서 만든다.

그래서

* 「원래 뭐였는지」 「누가 언제 왜 바꿨는지」 를 언제든 역추적할 수 있다
* 되돌리기가 그냥 이력 한 줄 삭제다
* 알고리즘 계산 코드를 손댈 필요가 없다

### 현재고를 저장하지 않는다

```
현재고 = stockDept(스냅샷) + Σ stock_transactions
부호  = 반납 +1 · 입고 +1 · 불출 -1 · 공용전환 -1
```

수량 필드를 고쳐 쓰면 두 번 반납했을 때 무엇이 맞는지 알 수 없게 된다.
사건을 기록하고 합을 낸다. 트랜잭션의 `qty` 는 **언제나 양수**로 넣고
부호는 읽는 쪽이 종류를 보고 정한다.

## 2. 키

```
PK = Qcode | DeptCode      예) Q1000108|SEO26FF
```

**자재코드 하나로는 부족하다.** 같은 자재가 부서마다 다른 재고와 다른
목표재고를 가진다. 743개 조합이 전체 모집단이고, 모든 테이블은 이 743을
기준으로 매핑된다. 여기 없는 코드를 화면이 쓰면 클릭이 헛돈다.

자재코드 형식은 `Q` + 7자리, 또는 `Q` + 영문 1자 + 6~7자리 (`QS418165`).
창고코드(`QFC01`)와 거래코드(`Q00101`)는 자리수가 달라 구분된다.

### 타입을 되돌리는 법 (반드시)

CSV 는 값을 전부 문자열로 만든다. `데이터/스키마.json` 에 컬럼별 타입이
적혀 있으니 **그대로 되돌린다.**

```
num    빈 칸은 null. 정수로 떨어지면 정수, 아니면 실수
bool   'O' 는 true, 'X' 는 false
list;  세미콜론으로 나눈 배열. 빈 문자열은 버린다
str    빈 칸은 null
```

> **실제로 당했다.** 재현 시험에서 `holdStd` 하나가 숫자 `1` 대신
> 문자열 `'1'` 로 남아 102행이 어긋났다. 이 값은 보험품 목표 산식에
> 들어가므로 문자열로 두면 **산식이 조용히 틀린다.**

## 4. 속성 결정 순서

```
1  3층 오버라이드가 있으면          그 값        typeSrc = 'override'
2  없고 알고리즘 판정이 확정이면    그 판정      typeSrc = 'algorithm'
3  그 외                            정본 Type   typeSrc = 'master'
```

확정은 **보험품과 계획품 둘뿐이다.** 회색지대와 배제는 판단을 못 내린
것이므로 정본 Type 을 유지한다. 회색지대를 「일치」 로 셈하면 알고리즘이
실제보다 잘한 것처럼 보인다.

승인할 수 있는 값도 보험품 · 계획품 둘뿐이다. 배제로 승인할 수는 없다.

## 5. 불변식 다섯 개

검사기가 자동으로 본다. 깨지면 화면끼리 어긋난 것이다.

| # | 불변식 | 왜 |
|---|---|---|
| 1 | 모든 화면의 자재코드가 정본 743 안에 있다 | 화면에 박아 둔 코드는 누르면 빈 화면이 뜬다 |
| 2 | 업무 화면 자재 ∩ 분석 화면 자재 ≠ ∅ | 전에 0종이었다. 화면을 넘나드는 흐름이 끊긴다 |
| 3 | 자재의 정체를 두 곳에서 정의하지 않는다 | 같은 코드가 화면마다 다른 자재였던 원인 |
| 4 | 모든 DeptCode 가 부서 테이블에 있다 | 부서 경로를 못 찾으면 빵조각이 코드로 뜬다 |
| 5 | 요약 숫자 = 행에서 다시 센 값 | 요약만 고치고 행은 안 고치는 실수를 잡는다 |

곁들여 보는 것

* 파생 테이블의 모든 행이 정본 키 공간 안에 있고, 행 수가 743과 같다
* `need` `action` 이 `target` 과 `stockDept` 로 다시 계산해도 같다
* 발주 신호 red · yellow · green 이 모두 존재한다 (건강도 얼굴 3종)
* QS 접두어 자재는 배제이거나 「보험품(QS 확정)」 이다
* `BASE_DATE` 가 설정 파일 한 곳에만 정의돼 있다
* 어댑터가 DB 보다 먼저 로드되지 않는다
* 소스에 제어문자(0x08 등)가 박혀 있지 않다 · 정규식의 역슬래시가 깨진 흔적

## 6. 조회 · 쓰기 API

화면이 쓰는 입구는 하나다. 화면은 CSV 나 층 구조를 직접 보지 않는다.

```
[ 조회 ]
DB.item(q, dept?)      · 한 건. dept 생략 시 세션 부서. 주소·문장에서 코드도 뽑는다
DB.list(filter?)       · 743건. filter 는 { 컬럼: 값 | 배열 | 함수 }
DB.find(text, limit?)  · 코드·품명 부분 일치
DB.dept(code)          · 부서 한 건
DB.equipment(name?)    · 설비
DB.maintenance(f?)     · 정비계획
DB.summary()           · 요약. 오버라이드가 반영된 재계산 값
DB.meta()              · 기준일 · 출처 · 건수 · 명세 상수

[ 쓰기 · 전부 3층에 이력으로 쌓인다 ]
DB.approveAttr({ q, dept?, newType, reason?, by?, at? })
DB.revertAttr(q, dept?)
DB.txn({ q, dept?, type, qty, note?, by?, at? })   · type 넷 중 하나 · qty 양수
DB.pool({ q, dept?, action?, note? })
DB.draft(kind, { q, dept?, data })

[ 이력 · 구독 ]
DB.changes()           · 3층 전체
DB.undo(table, seq)    · 한 줄 되돌리기
DB.reset()             · 3층 전부 비우기 (시연 초기화)
DB.on(fn) / DB.off(fn) · DB 가 바뀌면 부른다
DB.TXN_SIGN            · { 반납:+1, 입고:+1, 불출:-1, 공용전환:-1 }
DB.CONFIRMED_TYPES     · ['보험품','계획품']
```

`DB.item()` 이 돌려주는 행에는 층이 섞여 있고, 어느 층에서 왔는지 알 수 있다.

```
1층    name group wh price ltMean ltStd csp ceq proc recvDate eq
       baseType stockSeed stockAll suppliers
2층    verdict path why si sp conf grade target need amount action
       reason signal status sigKind stopDate dueDate dDays expect poolGrade
3층    type typeSrc override stock stockDelta txns pooled poolAction
계산   needNow    max(0, target - stock)      오버라이드 반영 후
       actionNow  발주 / 유지 / 감축          오버라이드 반영 후
```

`need` 와 `needNow` 를 구분한 이유 · `need` 는 알고리즘이 낸 값이라 근거
화면에서 그대로 보여 줘야 하고, `needNow` 는 반납 후의 지금 상태다.
반납하면 `needNow` 만 줄고 알고리즘 산출값은 그대로 남는다.

### 쓰기 전파

```
attr 화면에서 승인
  -> attribute_overrides 에 한 줄
  -> mtrl:db-change 이벤트
  -> 어댑터가 목록을 다시 자름
  -> 대시보드 · 적정재고 · 주간 리포트가 같이 바뀐다
```

실측 · 회색지대 한 건을 계획품으로 승인하면 보험품 382 → 381,
계획품 361 → 362 로 세 화면이 함께 움직인다.

## 7. 명세 상수 (`명세상수.json`)

화면이 규칙이나 상수를 새로 만들면 안 된다. 전부 이 파일에서 읽는다.

* 안전계수 **Z 는 등급별** · S 2.58 / A 2.05 / B 1.65 / C 1.28.
  **등급 캡(상한) 개념은 없다.** 유일한 상한은 리드타임창 부트스트랩 400회의
  관측상한이다
* 보험품 목표 = `min(ceil(μ_LT + SS), 관측상한)`,
  `μ_LT = 일평균소요 × 리드타임평균`, `SS = Z × 일표준편차 × sqrt(리드타임평균)`
* 계획품 목표 = 원칙 0. 핵심설비 · 최근 3년 소요 · 활발한 소요가 모두 맞을 때만 1
* 1단계 판정 = `si ≥ 55 & diff ≥ 15` → 보험품 / `sp ≥ 55 & diff ≤ -15` → 계획품 /
  그 외 회색지대. 신뢰도 `|diff| ≥ 25` HIGH · `≥ 15` MEDIUM · 그 외 LOW
* 등급 = 7요인 가중합 백분위 상위 5 / 20 / 60%.
  가중치 F5 공용성 0.50 · F1 핵심설비 0.35 · F3 리드타임 0.05 · F4 대체성 0.04 ·
  F6 고장확률 0.03 · F7 조달난이도 0.02 · F2 고장영향 0.01
* 발주 마감일 = `정지시작일 - (리드타임평균 + 선행일수 + 0.5 × 리드타임편차)`.
  선행일수 합리화 60 · 대수리 45 · 중수리 21 · 정기수리 14 · **교체휴지 10 ·
  공정휴지 7**
* 정체 = 최종입고 후 548일 이상 · 최근 무소요 · 재고 있음
* 금융비용 절감 = `(감축액 + 공용화 회수액) × 기여율 0.20 × 이자율 0.046`

### 도메인 규칙 (알고리즘 밖의 업무 규칙)

* **계획품은 Item Type 으로 정하지 않는다.** Consignment · 일일공급품 · 자가재는
  1단계에서 `배제-소모품` 으로 완전히 빠진다. VMI 는 계획품 점수 +10 신호일 뿐
* **순환품(Roll/Roller 계열)은 포함이 아니라 배제다** (`배제-순환품`)
* **배제가 QS 확정보다 상위 조건이다**
* PFC 창고 `QFC01` · 납기일 대비 사용예정일 30일 이상
* PFC 입고 후 180일 초과 → 공용자재 자동 전환
* Consignment 불출 후 3일 이내 원 창고 리턴 · 초과 시 중앙창고
* 반납 창고 `QVC70` 중고품 / `QVC75` 불용 / `QVC77` 중앙야적장 / `QVC01~05,08` 중앙창고
* 거래 `Q00101` 신품반납 / `Q00201` 중고반납 / `T00301` 투자자재
* 휴지구분 6종 · AD 대수리 · MR 중수리 · SD 정기수리 · CB 교체휴지 ·
  SB 공정휴지 · RM 합리화
* 반납 시 Account 는 최초 불출 계정과 같아야 한다 (현장 최다 실수)

데이터가 비어 있다는 뜻이 아니다.
