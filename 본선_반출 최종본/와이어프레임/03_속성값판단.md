## 무엇을 하는 화면인가

자재가 **보험품**(항상 재고를 들고 있어야 하는 것)인지 **계획품**(정비 일정에
맞춰 사면 되는 것)인지 알고리즘이 판정하고, **담당자가 승인**하는 화면.

핵심은 이것이다 · **현재 시스템에 「보험품 확정」 라벨이 0종이다.**
정답이 없으니 지도학습을 할 수 없다. 그래서 규칙으로 점수를 매겨 제안하고,
담당자 승인을 필수로 뒀다. **그 승인이 첫 라벨이 된다.**

## 목록 열

| 열 | 내용 |
| --- | --- |
| 자재명 | 굵게 + 아래 작은 글씨로 `부서 · 창고` 또는 설비명 |
| Q코드 | 자재코드 |
| 현재 → AI 판정 | `[현재 배지] → [AI 배지] [변경]` + 신뢰도 배지 |
| 보험품 / 계획품 점수 | `42.9 / 68.8` · 앞이 굵게 |
| 불출 24개월 | 횟수 |
| 재고금액 | 오른쪽 정렬 · 만원 |

정렬 · **바꿔야 할 것을 위로, 같은 칸 안에서는 재고금액이 큰 것을 위로.**
담당자가 위에서부터 처리하면 금액 큰 것을 먼저 본다.

```
보험품→계획품 · 계획품→보험품 · 현행유지 · 판정일치 · 배제
```

## 오른쪽 근거 패널

이 화면의 존재 이유다. **AI 가 왜 그렇게 판정했는지 전부 보여 준다.**

1. 자재 요약 (코드 · 부서 · 창고 · 재고 · 리드타임)
2. 큰 점수 + 판정 배지 + 신뢰도 + 기준선
3. 0(계획품) ↔ 100(보험품) 축 위에 두 점수를 찍은 막대
4. 보험품 점수 · 계획품 점수 각각 막대 + 한 줄 설명
5. 차이(si - sp)와 알고리즘 근거 목록 (점수를 만든 실제 값들)
6. 최근 24개월 월별 불출량 막대 그래프 (**직접 그린다. 차트 라이브러리 없음**)
7. 맨 아래 승인 버튼

버튼 문구는 판정에 따라 바뀐다 · 「AI 추천대로 계획품으로 변경」.
판정이 현재와 같으면 「현재 속성과 AI 판정이 같습니다. 변경할 필요가 없습니다.」

## 승인 흐름 (가장 중요)

```
[AI 추천대로 변경] 누름
  -> 확인 모달 · 사유를 고르거나 적는다
  -> DB.approveAttr({ q, dept, newType, reason })
  -> 3층 attribute_overrides 에 한 줄 쌓인다 (원본은 덮지 않는다)
  -> mtrl:db-change 이벤트
  -> 어댑터가 목록을 다시 자른다
  -> 이 화면 · 대시보드 · 적정재고 · 주간 리포트가 함께 바뀐다
```

**실측** · 회색지대 한 건을 계획품으로 승인하면
보험품 382 → 381 / 계획품 361 → 362 로 세 화면이 같이 움직인다.

승인 이력은 카드 아래에 쌓여 보인다 · 「승인 이력 N건 · 이것이 첫 라벨이 됩니다」.
**페이지 안 배열에 담지 말고 `DB.changes().attribute_overrides` 에서 읽는다.**
페이지 안에 담으면 화면을 옮기는 순간 사라진다.

## 뷰 전환

| 뷰 | 무엇을 보여 주나 |
| --- | --- |
| 실무자 뷰 | 위 목록 + 근거. 「내가 오늘 승인할 것」 |
| 관리자 뷰 | 판정 분포 도넛 · 신뢰도 분포 · 판정경로별 건수 · 부서별 확정률 |

부서가 하나뿐인 데이터라 **부서 일치도 대신 신뢰도 분포**를 보여 준다.

## 데이터 출처

`DB.list()` → 어댑터가 잘라 준 `ATTR_DATA` / `ATTR_SUMMARY`.
2차 버킷팅(다섯 칸)은 어댑터에서 한다. 파이썬 생성기 안에 숨기지 않는다.

**「회색지대」 는 화면에서 「현행유지」 로만 순화한다.** 내부 값과 CSV 는
회색지대를 유지한다. 「일치 확인」 이 아니라 「판단 보류」 라는 뜻이므로
신뢰도와 근거를 반드시 함께 낸다.
