# 재구축 프롬프트 (초기 버전)

> ## 이것보다 `프롬프트/` 폴더가 최신이다
>
> 이 문서는 CLI 하나로 만들 때의 순서다.
> **CLI 두 개(백엔드 · 프론트엔드)를 동시에 쓰기로 했으므로
> `프롬프트/00_공통규칙.md` 부터 시작한다.**
>
> 이 문서는 「데이터층을 어떻게 되살리는가」 를 한 곳에서 보고 싶을 때,
> 또는 CLI 를 하나만 쓰게 됐을 때의 대비책으로 남겨 둔다.
> 내용은 `프롬프트/A_백엔드_01~03` 과 같다.

본선에서는 기존 코드를 가져갈 수 없다. 이 폴더의 **CSV 와 문서만** 들고 간다.
아래 프롬프트를 그대로 붙여 넣으면 DB 층부터 다시 세울 수 있다.

순서대로 쓴다. 1번이 끝나야 2번이 의미가 있다.

CSV 는 UTF-8 BOM 이다 (Excel 이 한글을 열 수 있게). JSON 은 같은 데이터를
구조 그대로 담은 것이다. **급하면 JSON 을 그대로 쓰면 1번을 건너뛸 수 있다.**

## 1. 정본 · 파생 자산 만들기

> `본선_반출/DB_계약서.md` 를 먼저 읽어. 그게 이 작업의 규격이다.
>
> `본선_반출/데이터/` 의 CSV 를 읽어서 브라우저가 바로 쓸 수 있는 자산 두 개를
> 만들어 줘. 파이썬 생성기 하나로 둘 다 낸다. **생성기를 여럿 만들지 마라.**
> 전에 셋으로 나눠 놨더니 한 파일만 옛 값으로 남아서 화면마다 다른 판정을
> 보여 준 적이 있다.
>
> `assets/db-master.js`
>   `window.DB_MASTER = { meta, depts, materials, equipment, maintenance }`
>   1층 정본이다. 01 · 02 · 03 · 04 CSV 를 그대로 담는다.
>   `meta` 에 기준일 `2026-09-03` · 출처 · 건수를 넣는다.
>
> `assets/db-derived.js`
>   `window.DB_DERIVED = { meta, summary, attr, stock, pool }`
>   2층 파생이다. 05 · 06 · 07 CSV 와 `명세상수.json` · `요약값.json` 을 담는다.
>   `meta.spec` 에 명세 상수를 넣는다. 화면이 산식을 여기서 읽는다.
>
> 지킬 것
>   - PK 는 `Qcode|DeptCode` 다. 743개 조합이 전체 모집단이다.
>   - `attr` 과 `stock` 은 743행이어야 한다. 빠지면 화면이 반쪽만 본다.
>   - `stock` 의 `trend` 는 24개월 배열로 되살린다 (CSV 는 `;` 구분).
>   - `csp` `ceq` `active` 는 `O`/`X` 를 boolean 으로 되살린다.
>   - `stockDept` 는 소수가 나올 수 있다. 정수로 자르지 마라.
>   - 요약을 다시 계산하지 말고 `요약값.json` 을 그대로 실어라. 대신 아래
>     8번 검사에서 행으로부터 다시 세어 같은지 확인한다.
>   - JSON 은 `ensure_ascii=False` 로 쓴다. 한글이 깨지면 화면이 못 읽는다.
>   - 파이썬은 `PYTHONHASHSEED=0` 과 `PYTHONIOENCODING=utf-8` 로 돌린다.
>     해시 시드를 고정하지 않으면 집합 순서가 달라져 결과가 흔들린다.

## 2. 3층 오버라이드 저장소

> `assets/db-changes.js` 를 만들어 줘. 3층 오버라이드다.
>
> **원본을 절대 덮지 않는다.** 화면에서 한 일을 변경 이력으로만 쌓고,
> 읽는 쪽이 「오버라이드가 있으면 그걸 우선, 없으면 원본」 으로 겹쳐 본다.
> 그러면 원래 값과 변경자·시각을 언제든 역추적할 수 있고 알고리즘 계산
> 코드를 손댈 필요가 없다.
>
> 저장소는 `localStorage` 키 `mtrl.db.v1`. 서버가 없으니 브라우저가 정본이다.
> 바뀌면 `mtrl:db-change` 이벤트를 던지고, 다른 탭의 변경은 `storage`
> 이벤트로 받는다.
>
> 테이블 4개 · 계약서와 같은 컬럼 이름을 쓴다.
> ```
> attribute_overrides  q dept newType approvedBy approvedAt priorVerdict reason
> stock_transactions   q dept txnType qty txnAt processedBy note
> pooling_overrides    q dept action by at note
> pr_drafts            q dept data by at
> ```
> `seq` 는 화면이 만들지 않고 저장소가 붙인다.
> **선언한 컬럼만 통과시켜라.** 화면이 실수로 넣은 필드가 섞이면 나중에
> 무엇이 진짜 스키마인지 알 수 없게 된다.
>
> API · `KEY, all(), rows(t), add(t,row), remove(t,seq), clear(t), reset(), on(fn), off(fn)`

## 3. 조회 · 쓰기 API

> `assets/db.js` 를 만들어 줘. 화면이 쓰는 입구는 이 하나뿐이어야 한다.
> 화면이 `DB_MASTER` 나 `DB_DERIVED` 를 직접 읽으면 안 된다.
>
> 세 층을 겹쳐서 한 행을 만든다. 어느 층에서 온 값인지 알 수 있게 둔다.
>
> **속성 결정 순서** (이게 알고리즘 담당 규격이다)
> ```
> 1 오버라이드가 있으면        그 값       typeSrc = 'override'
> 2 알고리즘 판정이 확정이면    그 판정     typeSrc = 'algorithm'
> 3 그 외                      정본 Type  typeSrc = 'master'
> ```
> 확정은 보험품과 계획품 둘뿐이다. 회색지대와 배제는 판단을 못 내린
> 것이므로 정본 Type 을 유지한다.
>
> **현재고는 저장하지 않는다.**
> ```
> stock = stockDept(스냅샷) + Σ stock_transactions
> 부호 = 반납 +1 · 입고 +1 · 불출 -1 · 공용전환 -1
> ```
> `qty` 는 언제나 양수로 받고 부호는 종류가 정한다.
>
> `needNow` 와 `actionNow` 는 오버라이드가 반영된 지금 값이고, 알고리즘이 낸
> `need` `action` 은 그대로 남긴다. 근거 화면이 알고리즘 값을 보여 줘야 한다.
>
> API 시그니처는 계약서 6절 그대로 만들어 줘.
> 조회 `item list find dept equipment maintenance summary meta`
> 쓰기 `approveAttr revertAttr txn pool draft`
> 이력 `changes undo reset` · 구독 `on off` · 상수 `TXN_SIGN CONFIRMED_TYPES`
>
> 입력 검증을 넣어라. 정본에 없는 자재코드, 보험품·계획품이 아닌 승인값,
> 넷이 아닌 트랜잭션 종류, 0 이하의 수량은 예외를 던진다.
>
> `item()` 은 코드만 받지 말고 **문장이나 주소에서도 코드를 뽑아라.**
> QR 이 `material-view.html?code=Q4039953` 로 들어온다.

## 4. 업무 거래 상태

> `assets/db-biz.js` 를 만들어 줘. 08 · 09 · 10 · 11 CSV 를 담는다.
>
> **여기에 품명 · 단가 · 리드타임 · 등급을 두지 마라.** 자재의 정체는 정본
> 하나에만 있어야 한다. 전에 반납 화면과 구매 화면이 각자 품명을 들고 있다가
> 같은 코드가 서로 다른 자재가 됐다.
>
> 이 파일은 거래 상태만 든다 · 불출일 · 물품상태 · 잔여 · 계정 · 위치 ·
> 구매 가능 여부 · 신청 수량 · 작업주문.

## 5. 화면 어댑터

> `assets/analysis-data.js` 를 만들어 줘. `DB.list()` 와 `DB.summary()` 에서
> 각 화면이 쓰는 모양으로 잘라 주는 어댑터다. 자르는 규칙을 파이썬
> 생성기 안에 숨기지 말고 이 파일 하나에 보이게 둔다.
>
> `DB.on()` 으로 구독해서 DB 가 바뀌면 다시 자른다. `window.ANALYSIS.rebuild()`
> 로도 부를 수 있게 해 줘. 승인 한 번이 대시보드 · 적정재고 · 주간 리포트까지
> 바뀌어야 한다.
>
> 2차 버킷팅 · 1단계 판정을 정본 Type 과 비교해 다섯 칸으로 나눈다.
> ```
> 보험품→계획품 · 계획품→보험품 · 현행유지 · 판정일치 · 배제
> ```
> 목록은 변경이 필요한 것을 위로, 같은 칸 안에서는 재고금액 큰 것을 위로.
> 담당자가 위에서부터 처리하면 금액 큰 것을 먼저 본다.
>
> 화면 표시만 「회색지대」 를 **현행유지**로 순화한다. 내부 값과 CSV 는
> 회색지대를 유지한다. 「일치 확인」 이 아니라 「판단 보류」 라는 뜻이므로
> 신뢰도와 판단 근거를 함께 노출한다.

## 6. 로드 순서

> 모든 화면의 스크립트 순서는 이렇게 고정한다.
> ```
> config -> org -> nav -> popover -> wflow -> chat
>   -> db-master -> db-derived -> db-changes -> db -> db-biz
>   -> 어댑터(analysis-data / return-data / plan-data) -> tour
> ```
> 어댑터가 DB 보다 먼저 실행되면 **빈 배열을 만들고 오류도 안 난다.**
> 화면은 「대장 없음」 을 조용히 띄운다. 실제로 그 버그를 냈다.

## 7. 화면 규칙

> 화면은 계산하지 않는다. 명세가 정한 값을 그대로 보여 주는 뷰어다.
> 화면 쪽에서 규칙이나 상수를 새로 만들면 안 된다. 산식은 `meta.spec` 에서 읽는다.
>
> 요약 숫자를 하드코딩하지 마라. 산출 결과에서 매번 다시 센다.
>
> em-dash(U+2014)와 en-dash(U+2013)를 쓰지 마라. 가운뎃점(·)을 쓴다.
> 순수 검정(#000)을 쓰지 마라. 최고 명도는 `#1C1D22`.
> `null < 3` 은 자바스크립트에서 참이다. 마감일이 없는 건을 「지금 신청」 으로
> 세는 버그를 그렇게 냈다. null 을 먼저 걸러라.

## 8. 검사기

> `verify.py` 를 만들어 줘. DB 불변식 다섯 개를 검사한다.
> 결과는 콘솔이 아니라 **파일로 출력한다** (Windows 콘솔에서 한글이 깨진다).
>
> ```
> 1 모든 화면의 자재코드가 정본 743 안에 있다
>   따옴표 안만 보지 말고 주소에 박힌 코드까지 본다.
>   패턴은 \bQ[A-Z]?\d{6,7}\b. 창고(QFC01) 거래(Q00101)는 자리수로 걸러진다.
> 2 업무 화면 자재와 분석 화면 자재의 교집합이 비어 있지 않다
> 3 db-biz 에 품명 · 단가 · 리드타임 · 등급이 없다
> 4 모든 DeptCode 가 부서 테이블에 있다
> 5 요약 숫자가 행에서 다시 센 값과 같다
> ```
>
> 곁들여
> ```
> - 파생 행이 정본 키 공간 안에 있고 행 수가 743과 같다
> - need · action 을 target 과 stockDept 로 다시 계산해도 같다
> - 발주 신호 red · yellow · green 이 모두 있다
> - QS 자재는 배제이거나 보험품(QS 확정)이다
> - BASE_DATE 가 설정 파일 한 곳에만 있다
> - 어댑터가 DB 보다 먼저 로드되지 않는다
> - 소스에 제어문자(0x08)가 박혀 있지 않다
> ```
>
> **검사를 만들었으면 일부러 깨뜨려서 실패하는 것까지 확인해라.**
> 통과하는 것만 보면 검사가 사실은 아무것도 안 보고 있어도 알 수 없다.
> 실제로 정규식에 백스페이스 문자가 섞여 들어가 아무것도 매치하지 않는
> 검사가 조용히 통과한 적이 있다.

## 9. 시행착오 · 다시 하지 말 것

같은 실수를 두 번 하지 않기 위해 적어 둔다.

| 겪은 일 | 왜 그랬나 | 규칙 |
|---|---|---|
| 화면마다 자재가 달랐다 (교집합 0종) | 화면이 각자 더미를 들고 있었다 | 자재의 정체는 정본 한 곳 |
| 자재 검색만 옛 판정 (441 vs 302) | 생성기가 셋이었다 | 생성기는 하나 |
| 승인해도 대시보드가 안 바뀜 | 페이지 안 배열을 고쳤다 | 쓰기는 3층에, 구독으로 전파 |
| QR 이 안 읽혔다 | 형식정보 15비트를 LSB 부터 놓았다 | 내 인코더를 내 디코더로 검증하면 아무것도 검증되지 않는다. 남의 구현과 대조 |
| 「지금 신청」 이 6건 (실제 4건) | `null < 3` 이 참 | null 을 먼저 거른다 |
| 마감 D-null 이 화면에 출력 | 라벨 함수를 안 썼다 | 날짜는 라벨 함수로만 |
| 검사기가 조용히 통과 | 정규식에 0x08 이 섞였다 | 셸 heredoc 으로 정규식을 넘기지 말고 파일로 넘긴다 |
| 「반납 대장 없음」 이 뜸 | 어댑터를 DB 보다 먼저 로드 | 로드 순서를 검사한다 |
| 무재고 99.2% 를 데이터 오류로 착각 | 계획품은 재고 0 이 원칙 | 지표에 뜻을 붙여 쓴다 |
| 재무효과가 두 값 | 부서 기준과 전사 기준 | 어느 모집단인지 반드시 명시 |

## 10. 급할 때

CSV 를 파싱할 시간이 없으면 이 한 줄로 시작한다.

> `본선_반출/데이터/db-master.json` `db-derived.json` `db-biz.json` 을 각각
> `window.DB_MASTER = ` `window.DB_DERIVED = ` `window.DB_BIZ = ` 로 감싸
> `assets/` 에 넣어 줘. 그다음 `DB_계약서.md` 6절대로 `assets/db.js` 를 만들어 줘.

그러면 1 · 4번을 건너뛰고 3번부터 시작할 수 있다.
