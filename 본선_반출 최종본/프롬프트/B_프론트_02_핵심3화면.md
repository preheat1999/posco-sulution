# B · 프론트 02 · 핵심 3화면

**소요 예상 90~120분.** 시간이 모자라면 **이 셋만 있어도 시연이 된다.**
대시보드 · 속성값 판단 · 적정재고 분석. 이 셋이 과제의 답이다.

> **한 화면씩 따로 시킨다.** 세 개를 한꺼번에 시키면 셸이 화면마다 달라진다.

## 02-a · 대시보드 `main.html`

> **같이 첨부할 것**
> `와이어프레임/02_대시보드.md` · `이미지/main_pc.png` · `이미지/main_mobile.png`

> ## 할 일
>
> 대시보드를 만든다. **담당자가 아침에 켜면 오늘 무엇을 해야 하는지 3초 안에
> 알게 하는 화면**이다. 숫자를 나열하는 곳이 아니라 「지금 / 이번 주 / 기회 /
> 검토」 네 줄로 할 일을 내려 주는 곳이다.
>
> 첨부한 와이어프레임의 영역 구성을 그대로 따르고, 값은 전부 `window.DB` 에서
> 읽는다. **화면에 자재나 요약 숫자를 적어 두지 마라.**
>
> ### 특히 조심할 것
>
> ```
> null < 3 은 참이다
>   마감일이 없는 건(자재 확보 완료)을 「지금 신청」 으로 세면 안 된다
>   4건이 6건으로 나왔던 버그다. null 을 먼저 걸러라
>
> 건강도 얼굴은 색만으로 구분하지 않는다
>   7일 이상 웃음(초록) / 3~6일 무표정(주황) / 2일 이하·초과 찡그림(빨강)
>   표정 SVG 를 직접 그린다
>
> 진행 파이프라인은 선형이 아니다
>   단계마다 건이 쌓이는 모양이다. 가장 많이 걸린 단계가 병목이다
>   모바일에서는 세로로 눕히되 조각 네 개의 자리를 직접 지정한다
>   자동 배치에 맡기면 「QR 스 / 캔」 처럼 단계명이 반으로 쪼개진다
> ```
>
> ### 확인
>
> 만들고 나서 실제 숫자를 출력해 보여 줘라.
> ```
> 담당 설비 14기 · 담당 자재 743품목 · 보유 재고 49.7억원
> 보험품->계획품 149 · 계획품->보험품 90 · 회색지대 31
> 발주 필요 120 · 감축 대상 481
> 발주 마감 초과 4건
> ```

## 02-b · 속성값 판단 `attr.html`

> **같이 첨부할 것**
> `와이어프레임/03_속성값판단.md` · `이미지/attr_pc.png` · `이미지/attr_mobile.png`

> ## 할 일
>
> 자재가 보험품인지 계획품인지 알고리즘이 판정하고 **담당자가 승인**하는 화면.
>
> 이 화면의 존재 이유 · **현재 시스템에 「보험품 확정」 라벨이 0종이다.**
> 정답이 없으니 지도학습을 할 수 없다. 그래서 규칙으로 점수를 매겨 제안하고
> 담당자 승인을 필수로 뒀다. **그 승인이 첫 라벨이 된다.**
>
> 좌우 2열 · 왼쪽 목록 743행, 오른쪽 근거 패널.
> 행을 누르면 오른쪽이 그 자재로 바뀐다.
>
> ### 근거 패널이 이 화면의 핵심이다
>
> **AI 가 왜 그렇게 판정했는지 전부 보여 준다.** 숨기지 않는다.
> ```
> 큰 점수 + 판정 배지 + 신뢰도 + 기준선 50
> 0(계획품) <-> 100(보험품) 축 위에 두 점수를 찍은 막대
> 보험품 점수 · 계획품 점수 각각 막대 + 한 줄 설명
> 차이(si - sp) 와 알고리즘 근거 목록 (점수를 만든 실제 값들)
> 최근 24개월 월별 불출량 막대 그래프   <- 직접 그린다. 차트 라이브러리 없음
> ```
>
> ### 승인은 반드시 DB 로 간다
>
> ```
> DB.approveAttr({ q, dept, newType, reason })
> ```
> 페이지 안 배열을 고치면 화면을 옮기는 순간 사라지고 대시보드에도 반영 안 된다.
> 승인 이력도 `DB.changes().attribute_overrides` 에서 읽는다.
>
> 승인 후에는 `DB` 가 던지는 `mtrl:db-change` 를 받아 목록을 다시 만들고
> 화면을 다시 그린다. **한 번 승인하면 대시보드 · 적정재고 · 주간 리포트가
> 같이 바뀌어야 한다.**
>
> ### 2차 버킷팅 (다섯 칸)
>
> 1단계 판정을 정본 Type 과 비교해 나눈다.
> ```
> 보험품->계획품 · 계획품->보험품 · 현행유지 · 판정일치 · 배제
> ```
> 정렬은 **바꿔야 할 것을 위로, 같은 칸 안에서는 재고금액 큰 것을 위로.**
> 담당자가 위에서부터 처리하면 금액 큰 것을 먼저 본다.
>
> ### 말 조심
>
> 「회색지대」 는 화면에서만 **「현행유지」** 로 순화한다. 내부 값은 그대로 둔다.
> 「일치 확인」 이 아니라 **「판단 보류」** 라는 뜻이므로 신뢰도와 근거를 함께 낸다.
>
> ### 확인
>
> ```
> 743행이 다 그려지는가
> 회색지대 한 건을 승인하면 KPI 숫자가 움직이는가
> 승인 이력이 남는가
> 새로고침해도 이력이 남아 있는가 (localStorage)
> ```

## 02-c · 적정재고 분석 `stock.html`

> **같이 첨부할 것**
> `와이어프레임/04_적정재고분석.md` · `이미지/stock_pc.png` · `이미지/stock_mobile.png`

> ## 할 일
>
> 목표재고를 산출해 현재고와 비교하고 **발주 · 유지 · 감축**을 정하는 화면.
> 아코디언 5단이다.
>
> ```
> ① 산출 산식              접힘
> ② 재고 vs AI 적정재고 비교  접힘
> ③ 발주 필요 Alarm         펼침   <- 기본으로 열려 있다
> ④ 과잉재고 Alarming       펼침   <- 기본으로 열려 있다
> ⑤ 산출 제외 자재          접힘
> ```
>
> ### 아코디언 함정 (실제로 당했다)
>
> ```
> .sect:not(.open) > .sb { display:none }   <- 이걸 빠뜨리면 접히지 않는다
> ```
> 화살표만 돌아가고 내용은 그대로 있다. 그리고 화살표 방향을 반대로 두기 쉽다.
> **열림 = 위(∧) · 닫힘 = 아래(∨).**
>
> ### 산식은 화면이 계산하지 않는다
>
> `DB.meta().spec` 에서 읽어 그대로 보여 준다. 상수를 화면에 적지 마라.
>
> 특히 이것을 정확히 적어라.
> ```
> 안전계수 Z 는 등급별이다 · S 2.58 / A 2.05 / B 1.65 / C 1.28
> 등급 캡(상한) 개념은 없다. 유일한 상한은 리드타임창 부트스트랩 400회의 관측상한이다
> ```
> 이걸 헷갈리면 목표재고 설명이 통째로 틀린다.
>
> ### 무재고 99.2% 는 오류가 아니다
>
> **계획품은 상시 재고 0 이 원칙**이라서 그렇다.
> 화면에 그 뜻을 반드시 붙여 쓴다. 안 쓰면 데이터가 빈 줄로 오해받는다.
>
> ### 금액 단위
>
> 1억 넘으면 억원, 아니면 만원. **섞어 쓰지 마라.**
> `150,336만원` 은 읽을 수 없다. `15.03억원` 으로 쓴다.
>
> ### ② 비교 차트
>
> 가로 막대 두 줄(현재고 파랑 · 목표재고 초록) + 초과 구간 주황.
> **직접 그린다.** 오른쪽 배지로 수량/금액을 전환한다.
>
> ### 확인
>
> ```
> 발주 필요 120 · 감축 대상 481 · 현 수준 유지 142 = 743
> 아코디언이 실제로 접히고 펼쳐지는가
> 발주 신호 red · yellow · green 이 다 나오는가
> 행을 누르면 산식 근거가 열리는가
> ```
